# Contributing to QuickBuds

Thanks for helping. The most useful contribution is **a report from an owner of earbuds other than
the OnePlus Buds 4**. The writes for every other model come from HeyMelody's data. Owners have
confirmed only the realme Buds Air7 Pro and the OPPO Enco Buds2. Code contributions are welcome too. This page takes you from a clone to a running
build.

## Reporting a model

The quickest way is in the app: Settings › **Report a problem** (desktop: App settings). It sends the
log with your description, without Bluetooth addresses. For a longer exchange, open an
[issue](https://github.com/spizganed/QuickBuds/issues) with:

1. The earbuds' model and the phone (model, Android version).
2. What works and what does not. "The switch flips but nothing changes on the buds" is useful.
3. A log: in the app, Dev tools › **Clear**, try the features, then Dev tools › **Export**. The file
   lands in `Download/QuickBuds/`. Attach it as is.

For anything the app's log does not explain, [PACKET-CAPTURE.md](/docs/PACKET-CAPTURE.md) shows how to
capture the Bluetooth traffic itself, including what HeyMelody sends.

## Build quickstart

You need JDK 21 and the Android SDK with platform 37. Android Studio brings both; its bundled JBR
works as `JAVA_HOME`.

```bash
git clone https://github.com/spizganed/QuickBuds.git
cd QuickBuds
echo "sdk.dir=$HOME/Android/Sdk" > local.properties   # your SDK path
./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

- The first build downloads Gradle 9.6.0 through the wrapper. Nothing else to install: the only
  library is `androidx.core`.
- **A debug build cannot install over the release app** (different signing key). Uninstall the
  release first, and uninstall the debug build before going back.
- `./gradlew assembleRelease` without the release key builds an unsigned APK. That is expected.

Versions: Gradle 9.6.0, AGP 9.4.0, Kotlin 2.4.0, `compileSdk` / `targetSdk` 37, `minSdk` 26. AGP 9
compiles Kotlin itself, so do not add the `org.jetbrains.kotlin.android` plugin.

### Desktop app

Rust (stable). Windows needs nothing else; Linux needs BlueZ and the development packages for D-Bus, GTK 3,
and libayatana-appindicator (Arch: `dbus gtk3 libayatana-appindicator`).

```bash
cd desktop
cargo test
cargo run --release
```

Pair the earbuds in the system's Bluetooth settings first; the app connects to them once their audio
is connected. Icons, strings and `models.json` are read from the Android app at build time, so the two
apps never hold separate copies.

## Where things are

One module, `:app`, sources in `app/src/main/kotlin/com/spizganed/quickbuds/`:

| Package | What it holds |
|---|---|
| `bluetooth/` | The RFCOMM link, reconnects, the packet log (`BudsConnectionManager`, `BudsService`) |
| `protocol/` | Packet building and parsing (`OpoProtocol`, the parsers) |
| `ui/` | Activities, custom views, theming |
| `widget/` | Home screen widgets (layouts generated by `scripts/widget-layouts.py`) |

The desktop app is `desktop/`: `src/protocol.rs` (the same wire format), `src/session.rs` (the link),
`src/bt.rs` (Bluetooth sockets), `ui/app.slint` (the UI).

Per-model data (features, noise control modes, EQ presets, gestures) is in
`app/src/main/assets/models.json`.

Read before changing anything:

- [PROTOCOL.md](/docs/PROTOCOL.md): the wire format. Every claim is tagged with its source.
- [ROADMAP.md](/docs/ROADMAP.md): the plan, and the list of features decided against. Please check that
  list before proposing a feature.

## Rules that matter

- **Never guess a payload or a command number.** A wrong write to the buds fails silently. Capture
  what HeyMelody sends first ([PACKET-CAPTURE.md](/docs/PACKET-CAPTURE.md)), then read the result back.
- **Docs change with the code.** A protocol change comes with its PROTOCOL.md entry in the same commit.
- **A new user-visible string needs all 26 translations** (`app/src/main/res/values-*`). Machine
  drafts are fine. Lint does not catch a missing one; `scripts/check-locales.py` does, and CI runs it.
- No new dependencies, no Material Components. Every activity is portrait-locked by hand.
- Widget layouts are generated: edit `scripts/widget-layouts.py` and rerun it, never the XML.
- Test on real buds and say which model and firmware in the pull request.
- No vendor code, class names or file names in the repo, only the bytes on the wire.

## Pull requests

Fork, branch from `main`, keep one change per pull request, and describe what you tested on which
buds. The project is GPL-3.0-or-later; contributions are accepted under the same license.
